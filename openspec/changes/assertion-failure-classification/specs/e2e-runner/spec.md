## ADDED Requirements

### Requirement: Assertion Failure Classification
當步驟預期結果驗證判定為 **FAIL** 時，系統 MUST 產生該失敗之結構化分類，區分「業務性失敗（`business`）」與「操作性失敗（`operational`）」兩類：業務性失敗指動作已完成但頁面狀態與預期結果不符；操作性失敗指動作可能未完成或存在操作層障礙（如元素動態變化、等待失效）。該分類 MUST 由驗證模型基於頁面證據生成，系統 MUST NOT 以本地字串規則解析預期內容或頁面狀態而推定；當驗證節點未提供分類時，系統 SHALL 以 `operational` 作為預設值。此分類 SHALL 隨失敗回饋一併轉交執行器，供其後續決策區分「應補救」與「應收手」。

#### Scenario: 業務性失敗回饋引導執行器收手
- **WHEN** 驗證節點判定 FAIL 且將分類標記為 `business`（動作已完成但頁面狀態與預期結果不符）
- **THEN** 系統於執行器的步驟執行歷史中注入該失敗回饋，並附加「此為步驟預期結果未被滿足之失敗，完成要求的動作後應直接呼叫 `done_acting`，不得追加以改變失敗狀態」之意涵，使執行器不以翻轉失敗狀態為目的追加動作

#### Scenario: 操作性失敗回饋保留補救語意
- **WHEN** 驗證節點判定 FAIL 且將分類標記為 `operational`
- **THEN** 系統於執行器的步驟執行歷史中注入該失敗回饋，語意維持「動作可能未完成，可重新觀察或補救」，行為與現行失敗重試一致

#### Scenario: 無分類時以操作性失敗預設處理
- **WHEN** 驗證節點回傳未攜帶 `failure_type` 分類之失敗結果（如舊版本日誌或歷史執行之回饋）
- **THEN** 系統以 `operational` 處理該失敗回饋，執行器行為與現行一致，不產生收手指示
